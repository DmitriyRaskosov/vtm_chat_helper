# Аудит проекта trpg_chat_helper (состояние на 16.10.2026)

**Коротко.** Ядро проекта (Copilot-конвейер, дневник, схема БД) спроектировано продуманно, и его стоит защищать. Проблемы сосредоточены на периферии: HTTP-слой, авторизация, модуль World, фронтенд и документация. Попутно нашлось несколько фактических дефектов, а не только вопросов стиля: финальная запись дневника при уходе NPC из сцены никогда не срабатывает; в модуле World есть ссылки на несуществующие классы и методы; игрок получает список всех персонажей хроники. Документация в нескольких местах расходится с кодом. Всё ниже — констатация фактов, без предложений.

---

## 1. Карта проекта

**Предметная область.** Хроника → игровые сессии → сцены → сообщения. Персонажи (игроки и NPC) — это «сущности мира» (`world_entities`) с общим первичным ключом. Справочник канона VtM (`canon_*`) хранится отдельно и только читается.

**Backend, `app/`:**
- `Http/Controllers` — 13 контроллеров. Самые крупные: `ChatController` (356 строк), `CharacterSheetController` (353), `WorldRelationController` (308).
- Доменные сервисы разложены по папкам: `Character/`, `Scene/`, `World/`, `Messages/`.
- `Llm/`: `NpcCopilotService` делает два прохода к DeepSeek. Сначала извлекает темы (topics), затем генерирует 3 черновика реплики (reply).
- `Context/`: `ContextAssembler` собирает промпт из секций-провайдеров в пределах бюджета токенов. Цепочка объектов: `ContextRequest` → `ContextAssembly` → `ContextSection` → `ContextBuild`. Провайдеры лежат в `Context/Providers`.
- `Diary/`: запись L0 (`DiaryWriterService`), сводка сцены L1 (`DiarySummarizerService`), поиск (`DiaryRetrievalService`), предпросмотр (`DiaryPreviewService`), парсер метаданных.
- `Rag/` содержит интерфейс эмбеддингов и реализацию через Ollama. `Prompt/PromptRepository` загружает промпты из `resources/prompts/`.
- `Jobs/` — три задачи дневника. Их запускают контроллеры и `SceneParticipantService`.

**Поток Copilot:**
`POST /copilot/drafts` → `CopilotController` → `NpcCopilotService` → `ContextBuilder` → `ContextAssembler`. Сборщик опрашивает провайдеров: system, identity, scene, storyteller prompt, closing, recent messages, затем опциональные секции (relations, personality, biography, lore, diary). Дальше `DeepseekChatProvider` → разбор JSON → запись `CopilotRequest`.

**Поток дневника:**
- Каждые 15 сообщений `ChatController` запускает `WriteDiaryJob` (запись L0).
- При закрытии сцены `SceneController` запускает `SummarizeSceneDiaryJob` (дописывает L0 и делает L1).
- При уходе NPC из сцены `SceneParticipantService` запускает `WriteFinalDiaryJob`.
- В контекст Copilot дневник попадает через `DiaryProvider`: последняя запись плюс до двух семантически близких.

**Frontend, `frontend/src`:**
- Пять экранов: Login, Register, Chat, CharacterList, CharacterSheet, Diary.
- Три composable: `useSceneSession`, `useChatMessages`, `useCharacterSheet`.
- Один экземпляр axios в `auth.js`. Чат обновляется опросом сервера каждые 3 секунды. Pinia нет.

**БД.** 26 миграций. PostgreSQL используется активно: триггеры, CHECK-ограничения, частичные уникальные индексы, pgvector с индексом HNSW.

## 2. Архитектурные проблемы

### 2.1. Дефекты, найденные попутно (код не работает так, как задумано)

1. **Финальная запись дневника при уходе NPC никогда не выполняется.** В `app/Diary/DiaryWriterService.php:182` стоит условие `(int) $character->character_type->value !== 'npc'`. Целое число всегда строго не равно строке, поэтому метод сразу возвращает `false`. Задача `WriteFinalDiaryJob` запускается, но ничего не пишет.
2. **Ссылки на несуществующие классы:**
   - `WorldRelationException` используется в `WorldRelationService.php:46,65` и `WorldRelationController.php:14,108`;
   - `WorldRelationTypeException` — в `WorldRelationTypeValidator.php:14–31`;
   - `CannotDeleteWorldEntityException` — в `Models/WorldEntity.php:34`;
   - модель `WorldEvent` — в `WorldEntity.php:124–127`.

   Файлов ни для одного из этих классов нет.
3. **`WorldEntityService::updateSectFaction`** (`app/World/WorldEntityService.php:482–503`) вызывает несуществующие `assertSectFaction`, `$entity->coterie()` и `$entity->circle()`. Здесь же используется `Location::` без импорта (около строки 363). Похоже на остаток удалённых таблиц `coteries`/`circles`: в enum `WorldEntityType` есть случаи `Coterie` и `Circle`, а таблиц для них нет.
4. **Два файла с одним и тем же классом `App\Context\DiaryRenderer`:** `app/Context/DiaryRenderer.php` и `app/Diary/DiaryRenderer.php`. Пространство имён второго файла не соответствует папке, по PSR-4 он не загружается.
5. **Игрок видит всех персонажей хроники.** В `CharacterSheetController::index` (строки 117–128) вычисляется `$pcId`, но к запросу не применяется. Если у игрока есть свой персонаж, ему возвращается весь список.
6. **Фронтенд:**
   - `SheetAdvantagesSection.vue` использует `<TraitDots>` без импорта (строки 7–11), и глобально компонент не зарегистрирован;
   - `CharacterSheetView.vue:18` ссылается на необъявленную `compact`;
   - мёртвый компонент `SheetPlayBar.vue` импортирует `healthDamageKinds`, которого `useCharacterSheet` не экспортирует.
7. **В двух миграциях используется `DB::` без импорта фасада:** `2026_09_02_000001_create_messages_table.php` и `2026_09_11_000001_create_chronicles_and_attach_game_sessions.php`.

### 2.2. Дублирование логики

- **Поиск активной сцены** реализован дважды: `ChatController::resolveScene` (293–326) и `CopilotController::drafts` (29–45).
- **Проверка «персонаж из той же хроники и не в архиве»** с одинаковыми ответами 409 — в `ChatController::resolveWorldAuthor` (188–194) и `CopilotController::resolveNpcIdentity` (94–99).
- **Получение `canonical_name` по id** — минимум в 7 местах: Chat, Copilot, SceneContext, SceneParticipant, CharacterSheet, `CharacterSheetReader`, `Message::displayAuthor`.
- **Переименование с проверкой уникальности алиаса** — в `CharacterIdentityService::rename` (76–99) и `WorldEntityService::renameEntity` (457–479).
- **Поиск активных связей** есть и в контроллере (`WorldRelationController` 278–306), и в сервисе (`WorldRelationService` 94–147, 311–340).
- **Дневник: `DiaryWriterService` и `DiarySummarizerService`** скопированы по одной схеме: вызов LLM, разбор метаданных, эмбеддинг, сырой INSERT, обработка ошибок по каждому NPC, метод `regenerate*`. Функция `formatVector` повторена пять раз: Writer, Summarizer, Retrieval, `DiaryEntryController`, `ReembedDiaryCommand`.
- **`DiaryPreviewService` повторяет путь `DiaryProvider`,** включая `resolveRecentFirstMessageId`. Источник лимита истории при этом разный: в preview жёстко зашито `config('copilot.history_limit', 15)`, а провайдер берёт `historyLimit()` из запроса.
- **Лимит «3 записи дневника»** объявлен дважды: `DiaryProvider::LIMIT` и `DiaryRetrievalService::MAX_ENTRIES`.
- **Фронтенд:**
   - словарь меток «игрок/NPC» задан трижды: `useSceneSession.js:12`, `useCharacterSheet.js:5`, `CharacterListView.vue:87`;
   - проверка `isStoryteller` повторяется в шести местах;
   - конструкция `error.response?.data?.message ?? '…'` разбросана по всем view и composable;
   - таймер «сохранено, 2 секунды» есть в двух composable.

### 2.3. Laravel-конвенции: толстые контроллеры и смешение слоёв

- **`ChatController`** сам валидирует запрос (30–34, 140–142), делает прямые запросы Eloquent, открывает `DB::transaction` (79–125), содержит логику порога для запуска дневника (327–355), вручную сериализует ответ (228–247). Обращается к `auth()`, `request()` и `config()` изнутри приватных методов.
- **`CharacterSheetController::catalog`** (51–105) напрямую запрашивает канон. Три транзакции живут в контроллере.
- **`WorldRelationController`** держит в себе бизнес-проверки при создании связи (210–253).
- **`DiaryEntryController`** получает эмбеддинг-провайдер через `app(EmbeddingProvider::class)` и выполняет сырой `DB::statement` (69–74). При этом сервисы внедряются в методы, а не в конструктор, как в остальных контроллерах.
- **API Resource** есть только один, `UserResource`. Все остальные ответы — массивы `response()->json([...])` с приватными методами `serialize`/`listItem` в каждом контроллере.
- **`MessageEditService`** пишет в таблицу `character_diary_entries` через `DB::table` (78–86): модуль сообщений знает о схеме дневника.
- **`Chronicle::resolveId`** — статический метод модели, который вызывает `abort()`, то есть HTTP-побочный эффект в модели.
- **Хук `Message::booted`** достаёт `TokenEstimator` из контейнера через `app()`.
- **Правило «многошаговые записи — в транзакции» соблюдается не везде:** в `DiaryWriterService` INSERT записи и обновление `participant` (158–175) идут без транзакции, `DemoSeeder` тоже без транзакций.

### 2.4. Авторизация

- **Нет ни Policy, ни Gate.** Проверки используют четыре механизма: middleware `storyteller`, статический `CharacterAccess`, `authorize()` в FormRequest и разрозненные `abort` в контроллерах.
- **Членство пользователя в хронике нигде не проверяется.** `GET /messages`, `/scenes/{id}/context`, `/scenes/{id}/participants` и `/game-sessions/active` отдают данные любому авторизованному пользователю по id.
- **Проверки дублируются или противоречат друг другу:**
   - FormRequest повторно требует роль рассказчика там, где её уже проверил middleware (`StoreCharacterRequest`, `UpdateCharacterPlaceRequest`);
   - у `CopilotDraftsRequest::authorize` стоит `true`, хотя маршрут закрыт middleware;
   - для сущностей мира проверяется принадлежность к хронике, а для `archive`/`restore` персонажа — нет.
- **Фронтенд:** у маршрута `meta.storyteller` в `router.js:20` есть флаг, но guard его не читает. Глобального обработчика 401 нет.

### 2.5. Vue-конвенции

- **Где живёт логика.** `DiaryView.vue` (260 строк) и `CharacterListView.vue` (146) держат всю логику внутри view. `StorytellerCopilotPanel.vue` (250) сам вызывает API. Остальные экраны работают через composable.
- **`useCharacterSheet`** регистрирует `onMounted` и `watch(route)` внутри себя, то есть привязан к роутеру. Два других composable так не делают.
- **Глобальное состояние** — модульные `ref` в `auth.js`. Остальное состояние создаётся на каждый вызов composable.
- **Пробрасывание пропсов:** `SceneToolbar` получает около 20 пропсов и пять `v-model`. Секции листа персонажа изменяют объекты из пропсов через `v-model` на вложенных полях.
- **Мёртвые компоненты:** `SheetMeritsSection`, `SheetPlayBar`, `SheetOtherSection`, `SheetTraitSection`. Их стили остаются в глобальном `styles.css` (787 строк).
- **Неиспользуемые API-маршруты.** Из 9 маршрутов World фронтенд вызывает только два: `GET` и `POST /world/entities`. По Scope это ожидаемо, раз экран «Мир» убран.

### 2.6. Слепые зоны тестов

Всего 54 feature-теста и один пустой unit-тест (`ExampleTest`). Без покрытия:

- **Маршруты:** `logout`, `game-sessions` (оба), `catalog`, `PATCH /characters`, `disciplines`, `biography`, `archive`/`restore`, `GET context`/`participants`, уход участника из сцены, весь World (9 маршрутов), весь Diary CRUD/preview/regenerate (6).
- **`ContextAssembler` и все провайдеры** проверяются только косвенно, через один успешный сценарий Copilot. Бюджеты, порядок секций и отбрасывание опциональных секций напрямую не тестируются.
- **LLM-часть дневника.** Writer и Summarizer не тестируются: проверяется только факт запуска задачи. Именно поэтому дефект 2.1.1 остаётся незамеченным. Ветка семантического поиска (непустой запрос и эмбеддинг) не выполняется ни разу.
- **Подмена LLM в тестах** сделана через `Http::fake` по URL DeepSeek. `ChatProvider` и `EmbeddingProvider` в контейнере не подменяются, а именно так рекомендует `project.mdc`.
- **Авторизация:** нет тестов на то, что игрок видит или не видит, и на доступ к данным чужой хроники. Отсюда незамеченный 2.1.5.
- **Консольные команды** `demo:reset`, `canon:import-lore` и `diary:reembed` не тестируются.
- **Дублирование в тестах:** helper `createDiaryEntry` продублирован в `DiaryTest` и `MessageEditTest`. Unit-проверки парсера лежат в Feature-тестах.

### 2.7. Неочевидные зависимости

- **Цикл Context ↔ Diary.** `Context/Providers/DiaryProvider` импортирует `Diary\DiaryRetrievalService`, а `Diary\DiaryPreviewService` импортирует `Context\DiaryRenderer`, `LineTrimmer` и `TokenEstimator`.
- **Задачи запускаются из сервисов, а не только из контроллеров.** Сервис сцены (`SceneParticipantService`) запускает задачу дневника. Модуль сообщений (`MessageEditService`) пишет в таблицу дневника.
- **Character зависит от World:** `CharacterSheetReader`, `CharacterIdentityService` и `CharacterPlaceService` используют `WorldEntityService`/`WorldRelationService`. Цепочка зависимостей идёт контроллер листа → World → сцены (уход из сцен при архивации).
- **Темы из первого прохода Copilot не влияют на поиск в дневнике.** `DiaryProvider` берёт только `prompt`. Готовый `ContextRequest::retrievalQuery()` (prompt + top-2 темы) нигде не вызывается.
- **Версия промпта в `CopilotRequest`** всегда записывается от прохода reply, хотя запрос делает два прохода.

### 2.8. Расхождения со Scope.md и правилами

- **FK должен создаваться в `Schema::create` ссылающейся таблицы.** Нарушено:
   - `create_copilot_requests` добавляет FK в `messages`;
   - `create_chronicles_and_attach_game_sessions` — в `game_sessions`;
   - `create_characters_and_attach_message_authors` — в `messages` и `copilot_requests`;
   - ещё в пяти миграциях FK добавляются отдельным `Schema::table` уже после создания таблицы.
- **Правило «миграции — только схема» соблюдено:** вставок данных нет, `DB::statement` используется только для индексов, триггеров и CHECK.
- **Правило «строгая типизация» в `project.mdc`:** ни в одном PHP-файле нет `declare(strict_types=1)`.
- **Правило «enums вместо строк»:** строковые литералы остались там, где enum уже есть. Это `'npc'` (2.1.1), `'character'` в `WorldRelationService` 252/272 и в `Character`, `required_if:character_type,player`.
- **Канон и хроника не смешаны.** Таблицы хроники ссылаются на `canon_*` (`clan_id`, `sect_id`, `discipline_id`), обратных ссылок нет.

## 3. Стилистический разнобой

**Документы противоречат друг другу и коду:**
- `project.mdc` требует держать промпты в `SystemPromptProvider`, а Scope и код хранят их в `resources/prompts` через `PromptRepository`. Промпты дневника вообще не проходят через `SystemPromptProvider`. Заголовки секций и closing-инструкции строками зашиты в провайдерах.
- `project.mdc` называет замороженными Extraction, RAG-индексацию и memory-синхронизацию — этого кода больше нет.
- Scope сообщает о 25 тестах, по факту их 54.
- По Scope демо-данные — это 3 NPC (включая Ханну) и 15 сообщений. По факту `DemoSeeder` создаёт 5 других NPC и ни одного сообщения.
- README (строка 90) утверждает, что `DatabaseSeeder` запускает `DemoSeeder` при `local`. В коде этого нет.
- `docs/Architecture.md` пустой.
- В `composer.json` разрешён плагин Pest, хотя Pest не используется.

**Конфигурация расходится с кодом:**
- `config/character_sheet.php` нигде не читается.
- Из настроек секций в `context.php` используется только `max`. Ключи `min`, `priority`, `required` и `truncation` объявлены, но не читаются.
- `diary.write_timeout` не подключён: в задачах таймаут зашит как `$timeout = 540`.
- Значения по умолчанию в коде и в конфиге не совпадают. `topic_temperature`: 0.2 в коде, 0.1 в конфиге. `max_input_tokens`: 12000 в коде, 16000 в конфиге.
- В `DiaryWriterService` и `DiarySummarizerService` жёстко зашиты температуры и лимиты (2500/0.7, 0.4).

**Разные парадигмы в соседних файлах:**
- **Модели.** Новые объявляют поля атрибутом `#[Fillable]`, канонические — свойством `protected $fillable`.
- **Классы.** DTO в Context/Llm объявлены как `final readonly`. Сервисы почти всегда не final, кроме отдельных (`DiaryPreviewService`, `LineTrimmer`, `CharacterAccess`).
- **Возвращаемые данные.** Context использует типизированные DTO. Дневник возвращает массивы `array{created: …}`. Метаданные Copilot — вложенные массивы.
- **Ошибки.** В доменных исключениях на входе в контроллер — `abort()`, `HttpException` прямо из сервисов (`SceneContextService`, `MessageEditService`), `RuntimeException`. Дневник глушит ошибки в лог и возвращает `false` или список ошибок. `ValidationException` используется только в Login.
- **Внедрение зависимостей.** Где-то через конструктор с property promotion, где-то через параметры метода, где-то через `app()`.
- **Имена.** Файл называется `DeepSeekChatProvider.php`, а класс внутри — `DeepseekChatProvider`. Комментарии смешаны: русские и английские.
- **Сидеры.** Используются пять разных приёмов: `upsert` на модели, `DB::table()->upsert`, `insertOrIgnore`, `firstOrCreate`, `create`.
- **Миграции.** Нумерация с пропусками. `down()` в `create_canon_lore_tables` удаляет таблицу `canon_lore_chunks`, которую `up()` не создаёт.
- **Язык интерфейса.** Основной язык русский, но часть строк на английском: «Out Of Character», `Name`/`Nature`/`Demeanor`, «Game Chat», ключи эмоций (`joy`), `importance:`. Стили почти все глобальные, scoped-блок есть только в `DiaryView`.

**Мёртвый код:**
- `CharacterSheet` (DTO), `setExperience`, `learnPower`, `approve`, `current` (два разных), `findByAlias`, `setSect`, `WorldRelationTypeCatalog::keys`, `CanonClanRelation::relationsOf`;
- `ContextBuilder::build`, `NpcCopilotService::resolveModelName`, `ChatTurn::toAssistantMessage`;
- инфраструктура tool calls: `ToolCall` и ветка tool_calls в `DeepseekChatProvider` (production-код всегда передаёт пустой список инструментов);
- неиспользуемые импорты в `Character.php` и `CharacterSheetReader.php`.

## 4. Что работает хорошо и трогать не стоит

1. **Двухпроходный Copilot с бюджетом токенов.** Есть интерфейс `ContextProvider` и реестр по ключам. Обязательные и опциональные секции разделены, проход topics легче прохода reply. Метаданные сборки (что включено, что отброшено и почему, сколько токенов) сохраняются в `CopilotRequest`. Это ценный инструмент отладки.
2. **Модель курсоров дневника:** `last_diary_message_id`, `entered_message_id`, `left_message_id` в сочетании с порогом и итоговой сводкой при закрытии сцены.
3. **Пул поиска по дневнику.** Из пула исключаются записи, которые и так попадают в окно recent messages, с исключением для текущей сцены. Итоговый балл учитывает importance. Это хорошо покрыто тестами.
4. **`DiaryMetadataParser`** мягко переживает невалидный префикс: возвращает весь текст, метаданные — `null`.
5. **Задачи дневника** защищены от параллельных запусков через `ShouldBeUnique`.
6. **Интерфейсы `ChatProvider` и `EmbeddingProvider`** с выбором драйвера в `AppServiceProvider`.
7. **`PromptRepository`:** промпты в markdown с подстановкой переменных `{{var}}`.
8. **Схема БД переносит инварианты на уровень PostgreSQL:**
   - общий PK у `world_entities`, `characters` и `locations` с составными FK и CHECK по типу;
   - частичные уникальные индексы «одна активная сессия/сцена»;
   - триггеры: сущности мира нельзя удалить, версии биографии неизменяемы, уровни сил контролируются;
   - pgvector с HNSW.
9. **Чёткое разделение канона и хроники** по именам таблиц и сидерам. Канон заполняется идемпотентными upsert.
10. **Отдельные механизмы:** `SceneContextService` с оптимистичной блокировкой по `expectedRevision` и заморозкой при закрытии сцены. Версионирование биографии. Одноразовая привязка `CopilotRequest` к отправленному сообщению с блокировкой.
11. **`demo:reset`** сбрасывает данные игры без `migrate:fresh`, сохраняя канон и пользователей.
12. **Фронтенд:**
   - один экземпляр axios;
   - инкрементальная подгрузка чата по `after_id`;
   - защита от гонок при смене сцены;
   - защита опроса от повторного входа и очистка таймеров при размонтировании;
   - `defineModel` вместо ручных пар prop/emit;
   - всё написано на `<script setup>`.
13. **Стек и окружение** (Sail, PG18 + pgvector, отдельный worker, Ollama на хосте) последовательны и соответствуют правилам.
