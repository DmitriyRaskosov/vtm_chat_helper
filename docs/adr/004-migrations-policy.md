# ADR-004. Политика миграций

- **Status:** Accepted
- **Date:** 2026-10-16

## Context

26 миграций, из них часть нарушает правило «FK в `Schema::create` ссылающейся таблицы» (аудит §2.8), в двух `DB::` без импорта, `down()` в `create_canon_lore_tables` удаляет несозданную таблицу. Сокращение World (ADR-002) удаляет таблицы. Продакшен-данных нет: единственный инстанс — локальный, данные игры восстанавливаются `demo:reset` и сидерами. Накопление «исправляющих» миграций ради несуществующих данных только усложнит схему.

## Decision

1. **До первого релиза** схема правится в существующих файлах миграций. БД пересоздаётся `sail artisan migrate:fresh --seed`. Новые файлы миграций не создаются, имена существующих не меняются.
2. **После первого релиза** (момент фиксируется в `docs/Scope.md`) существующие миграции замораживаются, любые изменения — только новыми миграциями.
3. Каждая правка миграций сверяется дампом схемы `pg_dump --schema-only` до и после; все расхождения объясняются в отчёте задачи. Триггеры, CHECK и частичные индексы из `docs/ARCHITECTURE.md` §4 обязаны сохраниться.
4. Миграции содержат только схему; данные — в сидерах (`.cursor/rules/database.mdc`).
5. Пересоздание БД разрушает данные хроники в локальной БД. Перед задачей с правкой миграций пользователь сам решает, нужен ли дамп данных.

## Consequences

- Задачи 009, 010, 011, 015 и этап 3 (035) правят существующие файлы.
- Любой, кто подтягивает изменения, обязан выполнить `migrate:fresh --seed`; `migrate` поверх старой схемы не поддерживается до релиза.
- Решение пересматривается при появлении первых пользовательских данных, которые нельзя потерять.
- Исключение: если целевая таблица FK создаётся в более поздней миграции, допустимо добавить FK через DB::statement(ALTER TABLE ... ADD CONSTRAINT) в миграции целевой таблицы, с комментарием над вызовом. Пример: messages.author_character_id → characters (target в 000014).
