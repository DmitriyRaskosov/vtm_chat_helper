# ADR-005. Доменные исключения и единый маппинг в HTTP

- **Status:** Accepted
- **Date:** 2026-10-16

## Context

Аудит (§3): ошибки выражаются пятью способами — `abort()` в контроллерах и модели (`Chronicle::resolveId`), `HttpException` из сервисов (`SceneContextService`, `MessageEditService`), `RuntimeException`, `ValidationException` (только Login), молчаливый лог с `false` в дневнике. Код World ссылается на исключения, которых нет. Сервисы знают о HTTP, их нельзя вызвать из задачи или команды без побочных HTTP-эффектов.

## Decision

1. Базовый класс `App\Exceptions\DomainException` (abstract, наследует `\RuntimeException`). Каждый модуль объявляет свои исключения рядом с кодом: `app/<Module>/Exceptions/*Exception.php`.
2. Категории через промежуточные базовые классы или интерфейс с методом статуса:
   - `NotFound` → 404;
   - `Conflict` (архивный персонаж, чужая хроника, занятое имя на уровне состояния, устаревшая ревизия контекста) → 409;
   - `InvalidInput` (бизнес-валидация, которой нужна БД) → 422 в формате ошибок валидации Laravel (`message` + `errors`);
   - `Forbidden` — не используется: авторизация — в Policies (ADR-003).
3. Маппинг — только в `bootstrap/app.php` → `withExceptions()->render(...)`. Тело ответа — `{"message": "..."}` (и `errors` для 422), совместимо с текущим фронтом (`error.response.data.message`).
4. Сервисы и модели не вызывают `abort*()`, не бросают `HttpException`, не возвращают `response()`.
5. Задачи и команды ловят доменные исключения явно, логируют по правилу уровней (`docs/ARCHITECTURE.md` §8).
6. Внедрение — задача 018 (этап 2). На этапе 1 ссылки на несуществующие исключения удаляются вместе с кодом World (задачи 009, 010), новых не вводится.

## Consequences

- Коды ответов и тексты сообщений, которые видит фронт, не меняются — это проверяется тестами в задаче 018.
- Сервисы становятся вызываемыми из задач, команд и тестов без HTTP-контекста.
- Появляется ~10 небольших классов исключений — приемлемая цена за явность.
