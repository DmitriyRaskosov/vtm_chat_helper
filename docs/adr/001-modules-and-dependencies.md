# ADR-001. Модульная структура и направление зависимостей

- **Status:** Accepted
- **Date:** 2026-10-16

## Context

Код в `app/` уже разложен по модульным папкам (`Character`, `Scene`, `Messages`, `Diary`, `Context`, `Llm`, `Rag`, `Prompt`, `World`), но правила внутри модулей не зафиксированы. Аудит (§2.3, §2.7) показал: толстые контроллеры с транзакциями и запросами, запуск задач из сервисов, запись модуля сообщений в таблицу дневника, цикл зависимостей Context ↔ Diary. Проект ведёт один разработчик с помощью ИИ, поэтому правила должны быть простыми и проверяемыми grep-ом.

## Decision

1. Остаёмся на модульных папках в корне `app/` по стандарту Laravel. Не вводим `app/Domain`, DDD-слои, репозитории поверх Eloquent, CQRS.
2. Ответственность слоёв — как в `docs/ARCHITECTURE.md` §1: контроллер (authorize → сервис → Resource), FormRequest (валидация), Resource (сериализация), Policy (авторизация), сервис модуля (логика и транзакции).
3. Направление зависимостей — как в `docs/ARCHITECTURE.md` §2. Ключевые правила:
   - ни один модуль не импортирует `App\Context\*`; `Context` — потребитель только на чтение;
   - `dispatch()` — только из `Diary/DiaryScheduler`;
   - у каждой таблицы один модуль-владелец, остальные вызывают его методы;
   - `World` не зависит от остальных доменных модулей.
4. Цикл Context ↔ Diary разрывается: `DiaryPreviewService` переезжает в `Context`, `TokenEstimator` — в `Llm`.
5. DI — только через конструктор; `app()`/`resolve()` — только в service providers. DTO — `final readonly class`.

## Consequences

- Плюсы: правила проверяются grep-ом (`use App\Context` вне `app/Context`, `dispatch(` вне `DiaryScheduler`, `app(` вне `Providers`), понятны Composer без длинного контекста.
- Минусы: без Deptrac нарушение направления ловится только ревью и grep в DoD задач.
- Миграция идёт задачами 018–034 (этап 2). До их завершения код и документ расходятся — расхождения помечены в `docs/ARCHITECTURE.md` словом «сейчас».
