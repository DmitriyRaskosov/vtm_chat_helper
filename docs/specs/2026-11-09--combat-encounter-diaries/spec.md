# Spec: Боевая Секвенция (Этап 4: Дневник и Бой)

**Status:** Completed
**Date:** 2026-11-09

## 1. Контекст и Цель

Текущая система дневников (L0/L1) не учитывает боевые секвенции. Если бой длится долго, L1 при закрытии сцены может "проглотить" слишком много событий, потеряв детали. Кроме того, при наличии нескольких боев подряд или длинных пауз между ними, логика суммаризации ломается.

Цель — внедрить "слоёную" память. Бой становится отдельным смысловым блоком. Сообщения, написанные во время боя, получают привязку к секвенции. Система генерирует промежуточные L1 (до боя, во время, после), не смешивая их и не нарушая иерархию (L1 никогда не суммаризируются в L1).

Ограничение «1 L1 на сцену» было снято архитектурно.

## 2. User Stories

*   **US-1:** Как система, я хочу автоматически создавать промежуточный L1 перед началом боя, чтобы "зафиксировать" состояние сцены до кровопролития.
*   **US-2:** Как система, я хочу привязывать L0, созданные во время боя, к конкретной боевой секвенции.
*   **US-3:** Как система, я хочу создавать отдельный L1 по итогам боя (с флагом боевой сводки), чтобы NPC помнили именно боевые действия.
*   **US-4:** Как система, я хочу, чтобы при закрытии сцены создавался финальный L1 только из тех L0, которые еще не были суммаризированы в предыдущие L1.
*   **US-5:** Как система, я хочу, чтобы при выходе персонажа из сцены во время боя, для него генерировался L1 только из его боевых L0.
*   **US-6:** Как система, я не хочу допускать суммаризации L1 в другие L1 (нарушение иерархии).

## 3. Acceptance Criteria (EARS)

*   **AC-1 (Связь L0 с боем):** WHEN создается запись L0, THE system SHALL проверять наличие активной боевой секвенции на сцене. IF секвенция активна, THE system SHALL сохранять идентификатор этой секвенции в записи L0.
*   **AC-2 (Промежуточный L1 до боя):** WHEN бой начинается, THE system SHALL запускать суммаризацию всех необработанных L0 на сцене (не привязанных к другим боям) в один L1.
*   **AC-3 (Итоговый L1 боя):** WHEN бой завершается, THE system SHALL суммаризировать все L0, привязанные к этому бою, в один L1 (если их 2 и более). Этому L1 SHALL присваиваться идентификатор боевой секвенции.
*   **AC-4 (Финальный L1 сцены):** WHEN сцена закрывается, THE system SHALL суммаризировать только те L0, которые были созданы после завершения последнего L1 (используя `to_message_id` последнего L1 как курсор). L1 в L1 не суммаризируются.
*   **AC-5 (Выход из сцены):** WHEN персонаж покидает сцену во время активного боя, THE system SHALL создавать для него L1 из его L0, привязанных к этому бою (если их 2 и более).
*   **AC-6 (Правило одного L0):** IF для генерации L1 доступен только один L0, THE system SHALL не создавать L1 (оставляя L0 как есть).
*   **AC-7 (Множественные L1):** THE system SHALL разрешать создание нескольких L1 для одного NPC на одной сцене, если они покрывают разные временные промежутки (до боя, во время боя, после боя).
*   **AC-8 (Идемпотентность суммаризации):** WHEN вызывается суммаризация, THE system SHALL определять диапазон новых L0 на основе `to_message_id` последнего созданного L1. IF новых L0 меньше двух, THE system SHALL не создавать новую L1.

## 4. Out of Scope

*   Генерация L2 (иерархия заканчивается на L1).
*   Визуализация боевых L1 в интерфейсе дневника (отображаются как обычные L1 с приписками, чтобы человек различал).

## Post-Implementation Notes

- Убрана проверка «уже есть L1 на сцене» (`existingL1`, лог `diary.summarize.already_exists`). Курсор необработанных L0 — `max(to_message_id)` по всем L1 NPC на сцене; в выборку попадают только L0 с `from_message_id` больше курсора, `is_stale = false` и согласованным `combat_encounter_id` (конкретный бой или `null` для внесценовых хвостов).
- Фильтр боя: при суммаризации передаётся ID секвенции или `null`; L0 с другим `combat_encounter_id` в этот вызов не попадают. На одной сцене у одного NPC допускается несколько L1 (до боя, по бою, после) — подтверждено ручной проверкой БД/UI (3+ независимых L1).
- `CombatService::finishEncounter`: перед сменой статуса боя на «завершён» синхронно выполняется `WriteDiaryJob::dispatchSync`, чтобы боевые L0 успели записаться; затем `SummarizeSceneDiaryJob` с `$combatEncounterId`.
- `SummarizeSceneDiaryJob` принимает опциональные `$combatEncounterId` и `$characterId` (конструктор `($sceneId)` без аргументов сохранён). `uniqueId` джобы учитывает сцену, бой и NPC, чтобы параллельные сводки не блокировали друг друга. Вызовы — через `DiaryScheduler::scheduleSummary`.
- Точки интеграции: старт боя — суммаризация пре-боевых L0; финиш — боевых; выход из сцены во время боя — сводка только ушедшего NPC; закрытие сцены — прежний путь без параметра боя.
- Верификация: `tests/Feature/CombatDiaryTest.php` (в т.ч. `test_multiple_l1_per_scene_allowed`), полный `php artisan test`, Pint, PHPStan. Колонка `combat_encounter_id` в `character_diary_entries` из спеки sync-and-logs, миграция не дублировалась.
